# LogicMUS-Eval

Версионированный confirmation-выпуск статьи: [протокол и команды допуска](docs/confirmation-release.md).
Статусы научной фиксации, наборов, профилей, backend и реального smoke проверяются
раздельно; подготовка без моделей не означает готовности к основному запуску.

## Офлайн-анализ controlled-runner

```powershell
uv run --group analysis logicmus-eval analyze-controlled --run experiments/run-01 --plan examples/controlled-analysis.development.json --output experiments/analysis-dev-01
```

В development-примере замените UUID запуска и полный идентификатор модели на
сохранённые значения и заранее задайте контрасты. Это не окончательный план статьи.
Повторяемый `--run` принимает каталоги запусков или отчёты; `--no-plots` отключает
рисунки. Источники проверяются по manifest, инвентарю и журналу только для чтения,
без resume, endpoint и требования совпадения checkout с историческими исходниками.
Совместимость учитывает протокол, transport, метрики, исходники/runtime, модель,
условия инференса и схемы. Различия промптов direct/Z3 учитываются по стратегиям.

Таблицы `cases.csv`, `summary.csv`, `contrasts.csv`, диагностика, план/хеш и
идентичность journal snapshot сохраняются вместе. Графики читают эти же таблицы.
Оценки разделены по серии, паттерну, K, N, полной модели и стратегии; ошибки и отказы
остаются в знаменателях, неизвестные затраты — null. Основной MUS Exact Match
считается по всем эталонным UNSAT. Единица группировки — `family_id`: Wilson 95%
применяется при одном UNSAT на семейство, macro-F1 и парные разности используют
cluster percentile bootstrap (10 000 повторов, явный seed). Direct/Z3 сопоставляются
по `case_uid`, изменения N — по семьям внутри `noise_sweep`; неполные пары отклоняются.

Численные регрессии: Wilson 7/10 ≈ `[0.3968, 0.8922]`; контрпример macro-F1 даёт
P=R=1/2, F1=4/9. Интервалы pointwise, не одновременные; вырожденный bootstrap
маркируется, p-values и автоматических выводов о превосходстве нет. Diagnostic reruns,
development и confirmation не смешиваются; legacy доступен отдельно без придуманных
идентификаторов и статистической парности. Перед масштабным запуском остаются
фиксация confirmation-выборки/плана и проверка реально загруженных моделей и настроек.

[Методы, формат плана, проверки A–L и ограничения](docs/controlled-results-analysis.md).
Проверка реализации: **418 тестов**, ruff, strict mypy с Pydantic-плагином и pylint
прошли. Манифест публикуется атомарно: `complete` появляется после всех запрошенных
графиков; диагностика и рисунки включены в контроль целостности. Чтение, проверка и
хеширование запуска выполняются под одной блокировкой. Малые рисунки
на искусственных outcomes проверены визуально, без реальных LLM-запросов.

Пайплайн для генерации парных SAT/UNSAT логических бенчмарков с заданной
кардинальностью минимального невыполнимого подмножества требований (MUS),
строгой Z3-верификацией, проверкой единственности конфликта
и контролем лексической утечки. Включает модуль оценки LLM по двум стратегиям:
прямому текстовому выводу и нейросимвольной трансляции в Z3 (Python).

## Генератор v2: исправление экспериментального протокола

В новой генерации `mus_size=K` означает **ровно K требований в эталонном MUS**,
а не количество переменных. Наборы сохраняются как `dataset_v2.jsonl` и
`dataset_v2.manifest.json`. Опубликованный `datasets/v1.0` и исторические отчеты
не переписываются; у v1 параметр `mus_size` не всегда равен размеру ядра, поэтому
его нельзя напрямую сравнивать с v2. CLI evaluation продолжает читать v1.

| Паттерн | Допустимый K | Правил конструкции |
|---|---|---|
| direct | 2 | 2 |
| chain | >= 3 | K |
| fork | 3 | 4 (включая лишнюю ветвь) |
| coverage, idem | 3 | 3 |
| merge | 4 | 4 |
| math | >= 2 | K |

Генератор исключает конструкции, не помещающиеся в N. Каждый пример хранит
`metadata.pattern_id`, `pair_id`, `generator_version=2`. Выполнимость,
минимальность и единственность проверяются Z3; доказательство единственности
использует K проверок выполнимости всего набора после удаления каждого члена MUS.
Служебные CASE_ID/UUID не передаются модели. Имена переменных перемешиваются;
булевы атомы случайно заменяются их отрицаниями, а неравенства записываются в
случайной эквивалентной ориентации. Эти преобразования одинаковы внутри пары,
сохраняют логический статус и рендерятся из тех же полярностей, что использует Z3.

### Проверка поверхностных подсказок

Основная метрика проверки — **balanced accuracy**, случайный уровень **0.5**.
Используются TF-IDF word 1–2 и char_wb 3–5, логистическая регрессия и
StratifiedGroupKFold с группами SAT/UNSAT-пар (`pair_id`). Представления проверяются отдельно: `direct` содержит блок правил, а `z3` —
тот же блок и объявления переменных. Используются те же форматтеры, что в
промптах; постоянные инструкции не входят в признаки. Поле Var задает роли
переменных, а не противоречащую подписанному тексту формулу без отрицаний. Это тест поверхностной предсказуемости, а не доказательство отсутствия
всех утечек и не тест обобщения на новые текстовые пакеты.

Предел по умолчанию — **0.55** для обеих моделей признаков в каждом представлении глобально **и по каждому K**.
`--leakage-threshold` позволяет явно задать предел в [0.5, 1.0]. Значение 0.5 —
ориентир, а не гарантированный результат конечной выборки. Для небольших групп
случайные отклонения могут превышать 0.55; не следует подбирать seed до прохождения.
В манифесте сохраняются оценки каждого фолда, их стандартное отклонение,
положительная F1 (для справки), статус и `leakage_acceptance`.
`leakage_metrics_global` и `leakage_metrics_by_mus_size` показывают direct;
`leakage_metrics_by_input` хранит оба представления. Решение использует их все. Старый порог
F1=0.55 больше не используется: always-UNSAT на сбалансированной выборке имеет
F1=2/3, но balanced accuracy=0.5. CV-ошибка/недостаток пар дает `unavailable` и null,
а не фиктивный нулевой балл. Отклонения по фолдам не являются доверительным интервалом.

Если диагностика не пройдена, артефакты сохраняются для исследования, команда
завершается ошибкой, а evaluation отказывается запускать модели на таком v2-наборе.
Хеш датасета также должен совпадать с манифестом. Повышение порога — явное
ослабление критерия; оно фиксируется в манифесте. Эта защита не является границей
безопасности. V2 определяется по стандартному имени или метаданным строк,
поэтому переименование файла не отключает проверку. Настоящие внешние/v1-наборы
читаются по прежним правилам.

Небольшой локальный аудит заранее заданных seeds, без LLM:

```powershell
uv run python -m scripts.audit_generation --seeds 7 42 2026 --pairs 25 --rules 20 --output data/v2_audit.json
```

Аудит выводит **все** результаты, включая непрошедшие группы. Контрольный аудит
на 200 случаях для каждого из заранее заданных seeds дал:

| Seed | direct word / char | z3 word / char | Все проверки <= 0.55 |
|---|---|---|---|
| 7 | 0.450 / 0.505 | 0.455 / 0.470 | нет |
| 42 | 0.435 / 0.450 | 0.460 / 0.460 | нет |
| 2026 | 0.495 / 0.485 | 0.510 / 0.485 | да |

Глобальные оценки близки к случайному уровню, но у seed 42 direct word для K=3
равен 0.64. Глобальное усреднение не позволяет игнорировать этот результат.
Это не рекомендация выбирать seed 2026. Ни опубликованный эталон v2, ни новые
результаты LLM в этом PR не выпускаются. Прохождение порога конечным малым
набором не заменяет статистический анализ и проверку других поверхностных моделей.

Дополнительная отладочная калибровка с **100 парами на K** (800 случаев на seed)
на тех же трех seeds прошла все глобальные/групповые проверки обоих представлений.
Глобальные оценки лежали в **0.4925–0.5125**, то есть около 0.5. Этот размер
проверялся после результатов малого набора, поэтому это калибровка разработки,
а не заранее зарегистрированный подтверждающий эксперимент. Параметры и все
результаты обеих проверок: [JSON-аудит](docs/validation/generation-audit-2026-11-26.json).

## О проекте

Методология и эталонный датасет для оценки способности LLM выявлять
логические конфликты в спецификациях требований. Основной параметр задачи —
кардинальность MUS, обозначаемая $K$. Генератор создаёт SAT/UNSAT-пары с
контролируемым уровнем независимого шума, скрывая от модели различие между
смысловым ядром и шумом (нейтральные ID $R_1 \dots R_N$).

Ключевые элементы:

- **7 топологических паттернов конфликта**: `direct`, `chain`, `fork`,
  `merge`, `coverage`, `idem`, `math` — реализованы в
  `logicmus_eval/patterns/`.
- **Z3-оракул** для проверки SAT/UNSAT, валидности и минимальности MUS
  (`logicmus_eval/verifier.py`).
- **Независимая SMT-проверка единственности MUS** через удаление каждого члена ядра из всего набора (K вызовов решателя, `logicmus_eval/run_pipeline.py`). Legacy-структурная диагностика не используется как release gate v2.
- **Контроль лексической утечки** через TF-IDF + LogisticRegression с
  StratifiedGroupKFold по парам (порог balanced accuracy = 0.55, `logicmus_eval/leakage.py`).
- **Завершаемый процесс** для исполнения сгенерированного LLM кода на Z3
  (`logicmus_eval/sandbox/executor.py`).
- **Две стратегии оценки**: `direct` (прямой текстовый вывод) и
  `z3` (нейросимвольная трансляция в исполняемый Python + алгоритмическая
  минимизация `unsat_core`).

## Готовый датасет

В репозитории опубликована замороженная версия датасета — её можно
использовать напрямую, без повторной генерации:

- [`datasets/v1.0/dataset_v1_frozen.jsonl`](datasets/v1.0/dataset_v1_frozen.jsonl) —
  200 кейсов (100 SAT / 100 UNSAT).
- [`datasets/v1.0/dataset_v1_frozen.manifest.json`](datasets/v1.0/dataset_v1_frozen.manifest.json) —
  параметры генерации, версии окружения, результаты Z3-верификации,
  leakage-метрики.

Параметры v1.0: MUS = 2..5, `total_rules` = 20, `pairs_per_group` = 25,
`base_seed` = 42. Все кейсы прошли Z3-проверку: SAT-корректность 100/100,
UNSAT-корректность 100/100, MUS-валидность 100/100, MUS-минимальность 100/100,
уникальность MUS подтверждена для всех UNSAT-кейсов.

Пример оценки LLM на опубликованном датасете:

**bash**
```bash
uv run python -m logicmus_eval.cli evaluate \
    --strategy direct \
    --model-name openai/qwen2.5-coder-14b-instruct \
    --dataset-dir datasets/v1.0 \
    --limit 20 \
    --output-file evaluation_direct.json
```

**PowerShell**
```powershell
uv run python -m logicmus_eval.cli evaluate `
    --strategy direct `
    --model-name openai/qwen2.5-coder-14b-instruct `
    --dataset-dir datasets/v1.0 `
    --limit 20 `
    --output-file evaluation_direct.json
```

Для воспроизведения v1.0 используйте историческую версию генератора. Текущий генератор создает несовместимый по определению K набор v2; сохраняйте его в отдельный каталог.

## Структура

```
logicmus_eval/          # основной пакет
    cli.py              # CLI (Typer): generate, evaluate
    run_pipeline.py     # генерация + верификация + манифест
    evaluate_llm.py     # оценка LLM на датасете
    generator.py        # детерминированный генератор SAT/UNSAT пар
    verifier.py         # Z3-оракул + структурная проверка уникальности MUS
    extractor.py        # обёртка над litellm (structured output)
    hashing.py          # SHA-256 датасета, шаблонов и бандла исходников
    storage.py          # FileStorageManager
    templates.py        # шаблоны правил (5 текстовых пакетов + math_pack)
    patterns/           # 7 паттернов (chain, fork, merge, ...)
    evaluation/         # метрики, диагностика, пайплайн, стратегии
    models/             # pydantic-схемы (rules, test_case, manifests, ...)
    sandbox/executor.py # Z3CodeExecutor
scripts/                # экспериментальные скрипты (см. ниже)
tests/                  # unit + integration
datasets/               # опубликованные замороженные датасеты (в git)
data/                   # локальные артефакты генерации (gitignored)
experiments/            # результаты запусков (gitignored)
```

## Быстрый старт

**bash**
```bash
uv run python -m logicmus_eval.cli generate \
    --mus-size-min 2 --mus-size-max 5 \
    --pairs-per-group 25 \
    --total-rules 20 \
    --base-seed 42 \
    --output-dir data/generated_cases
```

**PowerShell**
```powershell
uv run python -m logicmus_eval.cli generate `
    --mus-size-min 2 --mus-size-max 5 `
    --pairs-per-group 25 `
    --total-rules 20 `
    --base-seed 42 `
    --output-dir data/generated_cases
```

После `uv sync` также доступен короткий entry point: `uv run logicmus-eval generate ...`.

Сохраняются:

- `data/generated_cases/dataset_v2.jsonl`
- `data/generated_cases/dataset_v2.manifest.json`

|---|---|---|

| `--mus-size-max` | `5` | Максимальная кардинальность MUS. |

| `--total-rules` | `20` | Общее число правил (core + noise). |
| `--base-seed` | `42` | Базовый seed генератора. |
| `--output-dir` | `data/generated_cases` | Каталог артефактов. |

## Эксперименты

Скрипты повторяют дизайн эксперимента из статьи: три серии на трёх моделях
(`Qwen2.5-Coder-14B`, `Gemma-4-E4B`, `GPT-OSS-20B`) и двух стратегиях.

### Smoke-grid

Быстрый прогон на одной модели, 7 конфигураций.

```bash
uv run python scripts/run_smoke_grid.py
```

### Full-grid

Полный прогон трёх серий эксперимента (EXP1: рост шума при $K=3$;
EXP2: рост $K$ при фиксированном $N$; EXP3: стресс-тест) со сменой
моделей на LM Studio.

```bash
uv run python scripts/run_full_grid.py --pairs 10 --context-length 4096
```

Требуется запущенный OpenAI-совместимый endpoint — см. раздел
[Подключение к LLM-серверу](#подключение-к-llm-серверу-для-запуска-оценки).

Скрипт возобновляем: уже существующие отчёты пропускаются.

### Проверка жизненного цикла моделей

Минимальный smoke-тест: загрузка → 1 инференс → выгрузка для каждой модели.

```bash
uv run python scripts/check_model_lifecycle.py
```

## Метрики

Новые отчеты имеют `report_schema_version: 3` и
`metric_definitions_version: "3"`. Это версии отчета и определений метрик,
независимые от версии генератора/датасета. Исторические JSON остаются читаемыми:
отсутствующие версии, статус и новые поля диагностики загружаются как `null`.
Их сохраненные значения метрик не пересчитываются и не получают новую семантику.
Исторические результаты и опубликованный v1 не изменяются.
Версия 2 читается с ее прежними определениями: объединенными ошибками и
request-only latency. Версия 3 разделяет ошибки и добавляет полное время случая;
эти новые измерения не восстанавливаются из старых отчетов автоматически.

Каждый обработанный случай создает ровно одну итоговую запись `details`.
Полноценный ответ (`valid_response`) имеет допустимую структуру, определенный
SAT/UNSAT, не содержит отказа или ошибки извлечения/исполнения. ID ядра должны
существовать во входных правилах; SAT с непустым ядром невалиден. Повторы ID
нормализуются как множество. Проверка полноценности не использует эталонный
SAT-ответ или эталонное ядро: обычный логически неверный ответ остается полноценным.
Исходный текст сохраняется в `raw_response`, включая ошибки JSON/схемы.

| Метрика | Что показывает |
|---|---|
| `sat_accuracy` | Корректные полноценные SAT/UNSAT-ответы / **все обработанные случаи**. Ошибки, отказы и отсутствие ответа дают нулевой вклад в числитель. |
| `valid_response_accuracy` | Корректные SAT/UNSAT-ответы / число полноценных ответов, включая логически неверные ответы в знаменателе. |
| `coverage` | Число полноценных ответов / все обработанные случаи. |
| `mus_exact_match` | Число полноценных ответов UNSAT с точным совпадением множества ID / все обработанные случаи с эталонным UNSAT. |
| `mus_precision` / `mus_recall` / `mus_f1` | Средние отдельных precision/recall/F1 по **всем эталонным UNSAT-случаям**. Ошибки, отказы, отсутствие ответа и предсказанный SAT дают нули. |
| `refusal_rate` | Доля кейсов, где модель отказалась рассуждать. |
| `infrastructure_error_rate` | Только исчерпанные API timeout/connection/rate-limit / все обработанные случаи; счетчик `infra_error_count`. |
| `response_error_rate` | Пустой ответ, ошибка JSON/схемы/извлечения, неизвестные ID, противоречивая структура или отсутствие SAT/UNSAT / все обработанные случаи; счетчик `response_error_count`. |
| `execution_error_rate` | Ошибка исполнения сгенерированного кода / все обработанные случаи; счетчик `execution_error_count`. |
| `total_tokens_consumed` / `total_thinking_tokens` | Суммы **известных** значений usage; `null`, если измерений нет. |
| `avg_prompt_tokens` / `avg_completion_tokens` / `avg_thinking_tokens` | Средние только по известным значениям соответствующего поля usage. |
| `total_execution_seconds` / `avg_latency_seconds` | Сумма/среднее `metadata.case_latency_seconds`: от подготовки промпта до итоговой записи случая, включая запросы, повторы/ожидания, разбор, валидацию и исполнение Z3. Сохранение отчета на диск сюда не входит. |
| `total_llm_seconds` / `avg_llm_latency_seconds` | Сумма/среднее `metadata.llm_latency_seconds`: только запросы к LLM, включая повторы и ожидания. |

Для отдельного UNSAT-случая с полноценным предсказанием UNSAT:
`P = |predicted ∩ expected| / |predicted|`,
`R = |predicted ∩ expected| / |expected|`,
`F1 = 2|predicted ∩ expected| / (|predicted| + |expected|)`.
Пустое предсказанное ядро дает нулевые P/R/F1. Итоговый `mus_f1` — **macro-F1**:
среднее F1 отдельных случаев, а не гармоническое средних P и R.
Промежуточные значения не округляются.

При отсутствующем знаменателе соответствующая метрика равна `null` с явным
счетчиком `0`: например, MUS-метрики на полностью SAT-выборке или условная
accuracy при отсутствии полноценных ответов. На непустой выборке из одних ошибок
`sat_accuracy = coverage = 0`, но `valid_response_accuracy = null`.

В `metrics` всегда есть `planned` (размер выбранного subset), `processed`,
`valid_responses_evaluated`, `unsat_evaluated`, `correct_sat`, `refusal_count`,
`error_count` и `error_counts` по основным классам ошибок. `total_evaluated` —
совместимый псевдоним `processed` в метрике SAT. Для завершенного запуска
`processed == len(details) == planned`, `status: "completed"`; сохраненный
промежуточный отчет имеет `status: "running"` и `run_info.finished_at: null`.
CLI сохраняет начальный отчет и накопленные результаты при завершении или
распространении неожиданной ошибки/прерывания. Прямые вызовы pipeline также
поддерживают сохранение после каждого случая (`save_each_case=True` по умолчанию).
Исключение распространяется вызывающему коду. Повторный запуск pipeline
сбрасывает прежние счетчики. Resume/checkpoints в этой версии не реализованы.
При жестком завершении процесса или сбое питания CLI не гарантирует сохранение
уже обработанных в памяти случаев.

Один случай может иметь несколько диагностических тегов, но `error_count`
учитывает его не более одного раза, с одной основной причиной в `error_counts`.
Отказ и ошибка могут пересекаться: например, отказ в некорректном JSON.
Поэтому складывать `refusal_count` и `error_count` как число разных случаев нельзя.
Повторы API не увеличивают число обработанных случаев.
Каждая ошибка имеет одну категорию `error_category`: `api`, `response` или
`execution`; категории не пересекаются и в сумме дают `error_count`.
Отказы учитываются отдельно и могут пересекаться с ошибкой ответа.

`metadata` записывает доступные usage и request latency **до** разбора JSON и схемы.
`case_latency_seconds` измеряется в pipeline также для неуспешных случаев.
Старое поле `metadata.latency_seconds` остается псевдонимом времени запроса;
оно никогда не переинтерпретируется как полное время случая.
Неизвестные значения — `null`, достоверно сообщенный ноль — `0`.
`usage_known_cases` и `usage_coverage` показывают количество и долю случаев
с измерением каждого поля usage; `latency_known_cases` и `latency_coverage` —
полноту измерения времени. `metadata.request_attempts` показывает число попыток.
`llm_latency_known_cases` и `llm_latency_coverage` отдельно показывают полноту
измерений запросов; `latency_known_cases`/`latency_coverage` в версии 3 относятся
к полному времени случая. Отсутствующие старые измерения остаются `null`.
`token_accounting_complete` истинно только на непустом запуске, когда для каждого
случая известен `total_tokens` и была ровно одна попытка. После успешного retry
usage успешного ответа сохраняется, но стоимость предыдущих неуспешных попыток
неизвестна: полная стоимость запуска не заявляется, оценки не придумываются.

Проверочные примеры: 16 правильных, один неправильный и три ошибки из 20 дают
`sat_accuracy = 0.8`, `valid_response_accuracy = 16/17`, `coverage = 17/20`.
Для UNSAT-случаев `(P,R,F1) = (1,1/2,2/3), (1/2,1,2/3), (0,0,0)`
итоги равны `mus_precision = mus_recall = 1/2`, `mus_f1 = 4/9`.

## Таксономия ошибок

Каждая запись в `details[*]` содержит `failure_tags`:

| Тег | Значение |
|---|---|
| `correct` | Ответ верен, MUS (для UNSAT) совпал. |
| `refusal_no_facts` | Модель заявила, что не может рассуждать. |
| `wrong_sat` | Ошибка в определении SAT/UNSAT. |
| `wrong_mus_missing` | UNSAT распознан, но часть MUS пропущена. |
| `wrong_mus_extra` | UNSAT распознан, но добавлены лишние правила. |
| `exec_error` | Ошибка исполнения сгенерированного кода Z3, этап `execution`. |
| `z3_timeout` | Истек общий deadline исполнения и доверенной проверки. |
| `z3_contract_error` | Нарушен контракт регистрации ограничений. |
| `z3_solver_unknown` | Обязательная проверка решателя вернула unknown. |
| `z3_worker_error` | Аварийное завершение worker, ошибка запуска или IPC. |
| `json_error` / `schema_error` | Ошибка JSON (`parse`) / схемы ответа (`schema`). |
| `empty_response` / `extraction_error` | Пустой ответ (`response`) / ошибка извлечения (`extraction`). |
| `api_timeout` / `api_connection` / `api_rate_limit` | Исчерпаны три попытки запроса, этап `request`. |
| `invalid_response` | Неизвестные ID или SAT с непустым ядром, этап `response_validation`. |
| `missing_answer` | Не определен SAT/UNSAT, этап `response_validation`. |
| `unknown` | Не попало ни в одну категорию (legacy-диагностика). |

Каждая ошибка также содержит `error`, `error_type` и `error_stage`. Ошибки JSON
и API не помечаются как ошибки Z3. Явный отказ провайдера сохраняется вместе
с текстом отказа. Ошибки конфигурации/программирования и прерывания родительского
evaluation не преобразуются в модельный результат. `SystemExit` и
`KeyboardInterrupt` внутри сгенерированной программы являются execution-ошибками
worker; родительский `KeyboardInterrupt` очищает worker и пробрасывается.
Все перечисленные ошибки Z3 относятся к категории `execution` и учитываются
один раз. Следующий случай продолжает обрабатываться. Допуск v2-датасетов
по манифесту и leakage audit по-прежнему проверяется до обращения к модели.

Эвристика отказа применяется к выделенному `reasoning`, а при ошибке JSON —
только к неструктурированному тексту. Произвольный `raw_response`, JSON и
сгенерированный код не сканируются целиком. Цитаты, fenced code и явное
отрицание утверждения об отказе исключаются. Явное поле отказа API учитывается
независимо от эвристики. Текстовая эвристика остается приближением: она не
доказывает намерение модели и не распознает все возможные формулировки отказа.

Grid runner, smoke runner и lifecycle-проверка проверяют содержимое отчета до
пропуска задания или записи успешного эксперимента. Версионный отчет должен
иметь `status: "completed"` и `planned == processed == len(details)`; при наличии
`run_info` требуется `finished_at` и согласованный счетчик. Поврежденный,
незавершенный отчет или неизвестная версия не считаются завершением. Старые
отчеты без версий и статуса требуют подтверждения: завершенный `run_info` либо
совпадение числа `details` с размером датасета с учетом лимита/плана манифеста.
Старый pipeline тоже мог сохранять промежуточные файлы без статуса. Если для
такого файла нет ни метаданных завершения, ни контекста ожидаемого числа случаев,
он остается читаемым, но не используется как доказательство завершения.

Анализ пропускает незавершенные отчеты и переносит версии в `summary.csv`.
`null` сохраняется как пустое числовое значение/NaN, без замены нулем. При
сравнении CSV без версии обозначаются как `legacy`; разные определения метрик
не удаляются как дубликаты и получают отдельные графики в `metrics_<version>`.
Исторические файлы не переписываются.

`mypy` и pre-commit проверяют весь `logicmus_eval` и `scripts` в режиме `strict`.
Статусы, типы, этапы и категории ошибок заданы `StrEnum`, JSON-значения типизированы.
Необоснованные `noqa`/`type: ignore` удалены. Для библиотек без stubs остаются
точечные `ignore[import-untyped]`; пояснены исключения pylint для существующей
CLI-оркестрации и намеренного исполнения/передачи исключений в sandbox.

### Контракт Python/Z3 и протокол исполнения 1

JSON-ответ модели сохраняет поле `python_z3_code`. Стратегия передает
`execute(code_str, expected_rule_ids)` только код и ID входных требований;
эталонные SAT/UNSAT и MUS исполнитель не получает. Принимается один
`solver = Solver()` без аргументов. Каждому входному ID должна соответствовать
ровно одна регистрация `solver.assert_and_track(boolean_expr, 'ID')`.
Python `True`/`False` допустимы как булевы константы; tracking ID должен быть
строкой. Пропущенные, неизвестные и повторные ID отклоняются. Отклоняются также
`add`, `+=`, `push/pop`, `reset`, `set`, assumptions, замена целевого solver,
дополнительные solver, тактики и альтернативные конструкторы. Нарушение
контракта сохраняется, даже если программа перехватила исключение.

Доступны `from z3 import Solver`, `from z3 import *`, `import z3` и `math`.
Все формы импорта получают один контролируемый Solver, а не исходный класс Z3.
Доступные конструкторы выражений и Python builtins перечислены в
`sandbox/allowed_names.py` (`EXPRESSION_NAMES`, `BUILTIN_NAMES`): Bool/Int/Real,
логические и арифметические выражения, кванторы, массивы, строки, битовые векторы
и множества. Вложенные импорты `z3.*`, SMT/file parsers, C API, явные контексты
и глобальные настройки не поддерживаются. Код выполняется в одном пространстве
имен; функции и генераторные выражения видят объявленные переменные.
Для совместимости разрешены наблюдения `check()`, `model()`, `assertions()`,
`reason_unknown()`, `unsat_core()`. Последний возвращает весь зарегистрированный
UNSAT-кандидат после проверки; это не минимальное ядро. Программа может вообще
не вызывать `check()`: итоговый вердикт и MUS вычисляются заново доверенным кодом.
Переменные модели `is_sat` и `conflict_core` игнорируются.

Каждый вызов запускает отдельный интерпретатор с собственным Z3-контекстом,
без зависимости от fork. На Windows запускается непосредственно базовый
интерпретатор с путями текущего окружения, минуя промежуточный venv launcher.
Общий monotonic wall-clock deadline (по умолчанию 5 секунд) включает подготовку
IPC, запуск, код, проверку контракта, SAT/UNSAT, минимизацию и получение ответа.
При превышении worker завершается через terminate, затем kill при необходимости;
на каждый из двух этапов очистки отведена 1 секунда. Очистка добавляется к
deadline, поэтому полное время возврата может быть больше заданного лимита.
Длительный системный вызов запуска/файлового ввода-вывода может задержать возврат;
успешный результат после истечения deadline не принимается.
Процесс ожидается, дескрипторы и временный JSON-файл закрываются при любом исходе,
включая прерывание родителя.

Через IPC передаются только JSON-данные в UTF-8: запрос через временный файл
stdin, ответ через pipe, вычитываемый `communicate` во время работы worker.
Это исключает ожидание завершения при заполненном выходном канале и блокирующую
запись большого запроса в Windows pipe. stdout/stderr сгенерированного Python
ограничены суммарно 8192 символами, ошибки — 8192 символами; лишняя диагностика
отбрасывается. Системный stderr worker перенаправлен в DEVNULL. Z3-объекты и
исключения не пересылаются.

Доверенный код проверяет зарегистрированные формулы в свежих solver без tracking
literals. SAT возвращает `is_sat=True, conflict_core=[]`. Для UNSAT deletion-based
минимизатор начинает со **всего** набора, перебирает ID в сортированном порядке и
удаляет ограничение только при UNSAT оставшегося подмножества. Затем повторно
проверяются невыполнимость ядра и выполнимость каждого одноэлементного удаления.
Любой `unknown` в обязательных проверках или истечение deadline дает неуспешный
результат без вердикта и ядра. Гарантируется subset-minimal MUS из входных ID;
минимальная мощность и единственность не гарантируются. При нескольких MUS
выбирается одно детерминированно, без обращения к эталону.

Новые отчеты стратегии Z3 содержат `z3_execution_protocol_version: "1"`, включая
пустые и незавершенные прогоны. Direct и старые JSON получают `null`/отсутствующее
поле. Это версия способа получения ответа: `metric_definitions_version` остается
`"3"`, исторические результаты не получают новых гарантий. Проверка ID не
доказывает правильность перевода естественного языка: семантически неверная
формализация может пройти исполнение и оценивается по эталону как прежде.

Код разделен по ответственности: `controlled_solver.py`, `solver_registry.py`
и `executor.py` содержат по одному основному классу. Проверки формул находятся в
`verification.py`, запуск/очистка процесса — в `process_lifecycle.py`, исключения —
в `errors.py`, публичные имена — в `allowed_names.py`, захват вывода — в
`bounded_output.py`. DTO протокола отделен от исполнения. Аналогично разделены
extractor, нормализация метаданных и реализации метрик; публичные импорты сохранены.

| `started_at`, `finished_at` | Метки времени (UTC). |
| `limit` | Лимит кейсов. |
| `total_cases_processed` | Обработано кейсов. |

Манифест датасета `dataset_v1_frozen.manifest.json`:

- `artifacts` — SHA-256 датасета и бандла исходников;
- `environment` — версии Python, z3, numpy, scikit-learn;
- `parameters` — MUS-размеры, пары на группу, всего кейсов, правил на кейс, seed;
- `validation_results` — результаты Z3-верификации (SAT/UNSAT/MUS/MUS-minimality);
- `leakage_metrics_global` — TF-IDF F1 (word и char) по всему датасету;
- `leakage_metrics_by_mus_size` — то же по каждому размеру MUS.

## Ограничения

- Промпты и шаблоны — русскоязычные; `evaluation/refusal_patterns.py`
  содержит legacy-паттерны на английском только для обратной совместимости
  с историческими отчётами.
- Процесс в `sandbox/executor.py` ограничивает время случайно зависшего кода.
  Ограниченные imports и отдельный процесс не являются полноценной защитой от
  произвольного враждебного Python: нет OS-изоляции файловой системы, сети,
  памяти или потомков процесса. Намеренная интроспекция Python/обход facade
  находятся вне поддерживаемого контракта. Для недоверенных атакующих программ
  необходима отдельная OS/container-политика.
- Пул предикатов (`templates.py::PREDICATE_POOL`) ограничен, поэтому
  `--total-rules` имеет верхнюю границу.
- Паттерны `coverage`, `idem` и `merge` определены только для фиксированных
  размеров MUS и в текущей версии не масштабируются на произвольное $K$.

# Возобновляемый controlled-run

Новый `controlled-v2` исправляет idem SAT-контрфакт: меняется только полярность
исходного факта; `controlled-v1` и исторические результаты сохранены.
[Аудит дубликатов](docs/validation/2026-11-28-idem-v2/README.md) воспроизводится офлайн.
Для короткой инфраструктурной проверки используйте
[development parent → фиксированный smoke](docs/development-infrastructure-smoke.md):
полный parent проходит прежний admission; 8 выбранных случаев дают 16 запросов
на модель, диагностический анализ и не являются исследовательской выборкой.
Исторический confirmation-v1 остаётся blocked.

Для уже допущенной серии PR #5 добавлены отдельная JSON-конфигурация инференса,
офлайн-проверка и журнал с возобновлением по случаям. Начните с
[небольшого примера](examples/controlled-run.example.json), указав свой
`series.manifest.json`, модель и параметры:

```powershell
# Только офлайн-проверка: без импорта LLM-клиента, HTTP и загрузки моделей.
uv run logicmus-eval experiment-preflight --config examples/controlled-run.example.json

# Реальный запуск и продолжение (эти команды обращаются к модели).
uv run logicmus-eval experiment-start --config examples/controlled-run.example.json --run-dir experiments/run-01
uv run logicmus-eval experiment-preflight --run-dir experiments/run-01
uv run logicmus-eval experiment-resume --run-dir experiments/run-01

# Явное разрешение повтора неопределенной HTTP-попытки с сохранением ее истории.
uv run logicmus-eval experiment-resume --run-dir experiments/run-01 --indeterminate-policy retry
```

Runner повторно проверяет допуск всей серии, план и все хеши; выполняет только
cell-файлы, без удвоения через combined. Перед HTTP фиксируется намерение,
после ответа — сырой ответ, затем — финальный outcome. Сохраненный ответ
обрабатывается без HTTP; завершенные ошибки и отказы не перезапрашиваются.
Сбой до фиксации ответа оставляет indeterminate: по умолчанию resume
останавливается. Exactly-once HTTP и отсутствие расходов при таком сбое
не гарантируются. SQLite `synchronous=EXTRA`, проверка цепочки и конца журнала,
транзакции и OS-lock обеспечивают восстановление при завершении процесса;
при потере питания гарантии зависят от локальной ФС, ОС и исправного хранения.

Manifest и outcomes сохраняют конфигурацию и фактические messages/schema/request
hash, ответы/IDs/finish_reason/usage/время, заданные и наблюдаемые сведения о
модели, версии метрик/Z3/runtime и хеш реальных Python-исходников. Неизвестное
остается неизвестным; принятые сервером параметры не считаются подтвержденными.
Изменения условий блокируют resume до HTTP. Секреты и HTTP-заголовки не пишутся.
`finish_reason=length`, проблемы контекста и неизвестный usage имеют явную
диагностику. Отчеты и метрики восстанавливаются только из финальных outcomes;
наличие ошибок модели не мешает завершенности всех запланированных случаев.

[Полное описание](docs/resumable-controlled-runner.md) содержит поведение после
сбоя на каждой стадии, проверку происхождения отчета, ограничения и диагностические
перезапуски. Все новые API-регрессии используют mocks и нулевой backoff; реальные
модели в разработке этого PR не запрашиваются и не загружаются. Готовность к
масштабному подтверждающему эксперименту не заявляется: окончательный набор
еще должен быть зафиксирован и допущен.

Проверки этого изменения: **374 теста пройдены** (`python -m pytest -q`),
`ruff check .`, `ruff format --check .`, `mypy` и `pylint` прошли.
Новые API-проверки выполняются через mocks, включая границу HTTP;
backoff в тестах нулевой.
